# ADR-0012 AccessLobby OIDC with explicit account linking

Status: proposed · 2026-10-10 · Implements the `accesslobby-oidc` part of ADR-0004 (ND-2) to the AccessLobby consumer contract v0.1 (MVP-PROVISIONAL, `docs/integration-contract-v0.1.md` in the AccessLobby repository, read 2026-10-10). Identity, session and schema code are gated classes. Registering POII as an AccessLobby client changes another peer: the request is `docs/runbooks/accesslobby-client-registration.md`; the owner approves and applies it, the agent never changes AccessLobby. Tested only against a MOCKED AccessLobby so far.

## Context

ADR-0004 asks for Authorization Code + PKCE S256 with `state` and `nonce`, discovery and JWKS validation, `GET /v1/me` resolution, storage of `(issuer, sub, person.id, local actor id)` with unique constraints, explicit linking with proof of both accounts, no email merge, no automatic fallback during an outage, and "this app only" / "all connected apps" sign-out with a verified back-channel logout endpoint. ADR-0009 put local sign-in on Better Auth 1.7.7 with account linking off, owner-only mode and an HTTP allow-list. Release one has one person who signs in: the owner.

The contract adds: pin the exact issuer; reject a discovery document naming another issuer or endpoints on another origin; validate the access token too (`aud=accesslobby-api`, `azp=<client>`); `GET /v1/me` answers `{ contract: "accesslobby.identity.v0.1", person: { id, status } }` (401 bad token, 403 suspended, 503 unavailable); a failed resolution fails the login closed; `sub` is not the durable person ID; the existing user links with "Connect AccessLobby" and the peer re-checks the old local session at the callback; logout tokens are checked for issuer, audience, signature, age, event and `sid`, and replays must never clear sessions; registration has exact redirect, post-logout and (same-origin) back-channel URLs; public clients with PKCE are the default profile.

## Better Auth mechanism: a POII plugin, not `genericOAuth`

Better Auth's `genericOAuth` plugin (1.7.7, read in `dist/plugins/generic-oauth` and `dist/api/routes/callback.mjs`, `dist/oauth2/link-account.mjs`) was evaluated first. It does discovery, PKCE, `nonce` binding and ID-token verification against the JWKS, but it does not fit POII's requirements:

| Requirement | `genericOAuth` + core `callback/:id` / `link-social` |
| --- | --- |
| Linking only by an explicit flow, `accountLinking.enabled: false` (ND-2) | `linkOAuthAccount` refuses every link while `accountLinking.enabled` is false, and requires matching emails unless `allowDifferentEmails`. Enabling it re-opens email-based implicit linking unless further flags are set. |
| An unlinked identity never creates a user and is refused as "not linked" | The callback looks up the account, then the user **by email**, then creates a user (only `disableSignUp` stops that, with a generic `signup_disabled` redirect). |
| `person.id` from `GET /v1/me` stored with unique constraints, checked on every sign-in | No hook between the token exchange and the session that knows whether this is a sign-in or a link. |
| Callback on the web origin (the browser never talks to the API) | The callback is `${baseURL}/callback/:id` on the API origin. |
| No automatic fallback, a clear error during an outage | Discovery runs once at start-up; if AccessLobby is down then, the provider is skipped for the life of the process. |
| Back-channel logout | Not provided. |

**Decision:** a small POII-owned Better Auth plugin (`apps/api/src/adapters/accesslobby-oidc.auth-plugin.ts`) adds the AccessLobby endpoints to Better Auth's own handler under `/v1/auth/accesslobby/*`. Better Auth still owns sessions (`internalAdapter.createSession`, `setSessionCookie`, `deleteUserSessions`), the signed cookie, the trusted-origin check, the rate limiter, the password check for unlinking (`password.checkPassword`), and the short-lived state rows (`auth_verification`, consumed atomically with `consumeVerificationValue`; logout `jti` tombstones with `reserveVerificationValue`). Better Auth's OAuth helpers build the authorization URL and the token request (`createAuthorizationURL`, `authorizationCodeRequest` from `better-auth/oauth2`, including the PKCE S256 challenge). `jose` 6.2.12 (already in the tree as Better Auth's dependency, now a direct dependency, pinned) verifies the three JWTs against the discovery JWKS. Nothing here hashes passwords or issues sessions itself.

The adapter name stays `local-signin`: AccessLobby is an additional way in on top of the password, enabled when `POII_ACCESSLOBBY_ISSUER` is set. A separate `accesslobby-oidc` adapter value would have to duplicate local sign-in, because linking starts from a password session and the password must keep working (no lockout). Setting the issuer under `local-owner` is refused at start. `local-owner` is unchanged.

## Flows

- **Start** (`POST /v1/auth/accesslobby/sign-in` or `/link`): discovery is fetched fresh (an outage answers `503 ACCESSLOBBY_UNAVAILABLE` before the browser leaves POII), then `state`, `nonce` and a PKCE verifier (random, 32/32/64 bytes) are stored in a Better Auth verification row keyed by SHA-256 of `state` for 10 minutes, with the intent, the SHA-256 of a **binding** secret and, for a link, the user and session that started it. The reply is `{ url, binding }`; the web app keeps `binding` in its own HttpOnly, SameSite=Lax cookie `poii_accesslobby_flow` (path `/signin/accesslobby`, 10 minutes). Linking sends `prompt=login`, so AccessLobby asks for a fresh login (proof of the AccessLobby account now).
- **Callback** (web `GET /signin/accesslobby/callback` → API `POST /v1/auth/accesslobby/callback` with `state`, `code`, `iss`, `error` and the binding): the flow row is consumed (single use; unknown, expired or wrong binding → `400 INVALID_FLOW`), `iss` must be the configured issuer when present (RFC 9207), then the code is exchanged with the verifier, the ID token is verified (JWKS, RS256, issuer, `aud` = client, `azp`, `exp`/`iat`, `nonce`), the access token is verified (JWKS, RS256, issuer, `aud=accesslobby-api`, `azp` = client, same `sub`), and `GET /v1/me` must answer an active person under contract v0.1. Any failure fails closed with a specific code; nothing is stored before all checks pass.
  - **Link:** the browser's current POII session must be exactly the session that started the flow (both proofs in one session; otherwise `401 LINK_SESSION_MISMATCH`). The link `(issuer, sub, person.id, auth user, actor)` is inserted; `(issuer, sub)`, `person_id` and the user are each unique, so a conflict is `409 IDENTITY_ALREADY_LINKED`, `PERSON_ALREADY_LINKED` or `ALREADY_LINKED` and is audited. The password session continues.
  - **Sign-in:** only a linked `(issuer, sub)` signs in; otherwise `403 NOT_LINKED` and nothing is created (no user, no account row, no session). The email in the ID token is never read. If AccessLobby now reports a different `person.id` for the linked `sub`, `409 IDENTITY_CONFLICT` (manual review). A Better Auth session is created for the linked user and its cookie set; the ID token and `sid` are kept in `accesslobby_session` for `id_token_hint` and `sid` lookups.
- **Unlink** (`POST /v1/auth/accesslobby/unlink { password }`): the local password is required (Better Auth's check, rate limited 3 per 10 s), so the owner can never end up with neither way in. Removes the link and ends the other sessions that came from AccessLobby.
- **Sign-out.** "This app only" is Better Auth's `/sign-out` (unchanged). "All connected apps" (`POST /v1/auth/accesslobby/sign-out-all`) ends every POII session of the owner first, then returns AccessLobby's `end_session_endpoint` with `id_token_hint` (when this session came from AccessLobby), `client_id` and the registered `post_logout_redirect_uri`; when AccessLobby cannot be reached it returns `null` and the web app says that AccessLobby's own session may still be active. "Every device" stays Better Auth's `/revoke-sessions`.
- **Back-channel logout** (`POST /v1/auth/accesslobby/backchannel-logout`, relayed by the web route `/signin/accesslobby/backchannel-logout`, which is the registered URL): no cookie, no CSRF header, no Origin; Better Auth's origin check only applies to cookie-carrying requests. The `logout_token` must verify against the JWKS (RS256, issuer, `aud` = client), be at most 5 minutes old (`iat`, 5 s clock tolerance), carry exactly the back-channel logout event, a `jti`, `sub` and/or `sid`, and no `nonce`. A `jti` is accepted once (atomic tombstone for 15 minutes; expired flow and tombstone rows are purged whenever a flow starts or a logout token arrives). Invalid or replayed → `400 INVALID_LOGOUT_TOKEN` and nothing is revoked. Valid → `200` whether or not the subject is known (no oracle); if the `sub` (or, without `sub`, the `sid` of a recorded AccessLobby session) belongs to the linked user, **every** POII session of that user ends.

## Data (migration `0005_accesslobby_identity_link`, expand only)

- `identity_link`: `id`, `issuer`, `subject`, `person_id`, `auth_user_id` (FK `auth_user`, cascade), `actor_id` (FK `actor`, set null; refreshed at the next AccessLobby sign-in after a restore), `linked_at`, `last_sign_in_at`. Unique: `(issuer, subject)`, `(person_id)`, `(auth_user_id)`.
- `accesslobby_session`: `session_id` (PK, FK `auth_session`, cascade), `issuer`, `subject`, `sid`, `id_token`, `created_at`; index `(issuer, sid)`.
- Better Auth's tables are not changed. No access or refresh token is stored. Neither table is part of backups (like the other `auth_*` tables).

## Configuration

`POII_ACCESSLOBBY_ISSUER` (exact; https, or http only on localhost), `POII_ACCESSLOBBY_CLIENT_ID`, `POII_ACCESSLOBBY_API_URL` (AccessLobby API base for `/v1/me`), optional `POII_ACCESSLOBBY_CLIENT_SECRET` (confidential client, `client_secret_basic`; default public client with PKCE, `token_endpoint_auth_method=none`), `POII_ACCESSLOBBY_API_AUDIENCE` (default `accesslobby-api`), `POII_ACCESSLOBBY_REDIRECT_URI` and `POII_ACCESSLOBBY_POST_LOGOUT_REDIRECT_URI` (defaults `WEB_BASE_URL` + `/signin/accesslobby/callback` and `/signin/accesslobby/signed-out`), `POII_ACCESSLOBBY_TIMEOUT_MS` (default 5000 for every call to AccessLobby). Scope `openid` only: POII reads `sub` and `sid` and nothing else, so it asks for nothing else (the contract allows `openid profile email`). Server-side calls never follow redirects. Discovery is cached for 10 minutes (fresh at every flow start and at "all connected apps"); JWKS rotation is handled by jose (an unknown `kid` refetches, 30 s cool-down).

## Web

The sign-in page shows "Sign in with AccessLobby" when the API reports it configured. A new Account page (linked from the navigation when signed in) shows how the session signed in, "Connect AccessLobby" or the link with "Disconnect" (password field), and the sign-out choices "This app only", "All connected apps" and "Every device". The callback, post-logout and back-channel routes live under `/signin/accesslobby/`, which the request proxy already skips, so neither the session redirect nor the cross-site refusal applies to AccessLobby's redirect and server-to-server POST.

## Consequences and residual risks

- **No automatic fallback.** While AccessLobby is down its button fails with a clear message and nothing changes; the password form on the same page works as before. That is the owner's choice to use, not a fallback.
- **Back-channel scope is wider than the contract's `sid` matching.** A valid logout token for the owner ends every POII session, including password sessions on other devices, because in owner-only mode a password session is not tied to any AccessLobby `sid`. Erring towards more revocation costs at most a new sign-in. Revisit when several people sign in.
- **"All connected apps" also ends every POII session**, not only this browser's (the contract says all apps does not mean all devices; for POII it does). Same reason; revisit with the above.
- **Delivery is not guaranteed.** If POII is unreachable when AccessLobby sends the logout token, POII sessions live until they expire (`POII_SESSION_TTL_HOURS`, default 14 days). There is no periodic issuer-session check. Shorter sessions are the mitigation if needed.
- **Locally**, AccessLobby's IAM container must be able to reach the web app's registered back-channel URL; with `http://localhost:3000` inside Docker it usually cannot, so back-channel logout is exercised on staging.
- **Tests use a MOCKED AccessLobby** (`apps/api/test/accesslobby-mock.ts`). Nothing here claims AccessLobby has registered POII or that the flow ran against the real issuer.
- **Owner-only.** Exactly one link can exist (the owner's). A second person signing in with AccessLobby needs a contract migration of `auth_user_single_owner` and a decision about Join (`prompt=create`), which the contract describes and POII does not implement.
