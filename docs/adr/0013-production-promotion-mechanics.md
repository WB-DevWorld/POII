# ADR-0013 Production promotion mechanics

Status: proposed · 2026-11-25 · Implements release policy step 4 (ADR-0006) and mirrors the staging mechanics (ADR-0010). Never run: no production exists, and the first activation needs the owner's phrase. Runbook: `docs/runbooks/production-deploy.md`.

## Decision

- **Trigger and switch.** `Deploy production` runs after each successful `Deploy staging` run on `main`, and by manual dispatch with a source SHA. It is a no-op until the repository variable `POII_PRODUCTION_ENABLED` is `true`; a manual `dry_run` only reads GitHub and Dokploy and is allowed while it is off.
- **What gets promoted.** The source SHA and both image digests come from the staging run's release manifest artifact, never from a tag or a guess. The manifest must say `environment: staging` and `observedReadyVersion` equal to `sourceSha`: it is the proof that staging served that source. The digests must also match what the GHCR `sha-<sha>` tags point at. Nothing is rebuilt.
- **Promotion class, decided per range.** A digest contains every commit before it, so the class is decided for the whole range since the previous production deploy, not for the last commit. It is `routine` only if every commit in that range came in through a merged pull request into `main` that carries `risk:routine` and not `risk:gated` (the labels the required `classify` check sets from the base-branch policy). It is `gated` if any pull request is `risk:gated`, a commit has no such pull request, a label is missing, there is no previous production deploy (so the first deploy is always gated), the previous source is not an ancestor of the new one (a rollback), the source is the one production already runs, the range has more than 500 commits, or GitHub cannot answer. Unclassified counts as gated. The logic is `infra/scripts/promotion-class.mjs`, with tests against a mocked API.
- **Previous production source.** It is read from the manifest artifact of the newest successful `Deploy production` run, through the GitHub API. If that history cannot be read at all, the run stops instead of asking for approval: nothing is promoted while the state of production is unknown. If the artifact has expired (90 days), the promotion is gated.
- **Environment.** A routine promotion runs in the `production` environment (no reviewers). Everything else runs in `production-gated`, where the owner is the required reviewer, so the run waits for the owner's click. The workflow selects `production` only for the exact value `routine`. Both environments hold the same Dokploy secrets and are limited to `main`. The `gate` job that decides the class has no environment and no secrets.
- **Order.** All deploys share one concurrency group and are never cancelled in progress; a dry run has a group of its own. Because the class covers the whole range, every run that arrives while a gated change is not yet in production is itself gated: a routine change never overtakes a gated one. The deploy job looks at the production history again after any approval. A run for a source that production has already passed ends without touching Dokploy; a routine run whose range has grown into a gated one fails.
- **Same source again.** A staging redeploy of the source production already runs promotes nothing. A manual dispatch can redeploy it; that is gated.
- **Deploy and evidence.** As on staging: `dokploy-deploy.mjs` rewrites `API_IMAGE`, `WEB_IMAGE` and `GIT_SHA` of the production Compose service and deploys, after checking that the service's own `WEB_BASE_URL` is the production one (a new optional check, `EXPECT_WEB_BASE_URL`, so a compose id of the staging service cannot be deployed to by mistake); `staging-smoke.sh` waits for the SHA on the production host and runs its checks there. The manifest `production-<UTC time>-<sha12>.json` adds `promotedFrom` (the staging manifest) and `promotionClass`, is uploaded as an artifact and is recorded under `infra/releases/` through a normal PR.
- **Failure.** Nothing is rolled back or cancelled automatically (as ADR-0010). A failed run writes no manifest, so the next promotion is classified from the last deploy that passed every check.

## Alternatives considered

- **Every production deploy gated.** Simplest, and safe. It contradicts policy step 4 ("routine releases go out without the owner") and trains the owner to click through. It remains the behaviour whenever anything is unclear.
- **Classify by changed paths at promotion time instead of by PR labels.** It would not depend on labels, which anyone with triage rights can still edit after the merge. But it needs a second implementation of the classifier that must stay identical to `risk-classify.yml`, it must choose which version of `risk-classes.json` judges an old commit, it loses a class raised by label, and the compare API lists at most 300 files. The label is the recorded outcome of the required check at merge time, so it is used. A path check could later be added as a second condition (both must say routine).
- **Classify only the newest commit.** Wrong for cumulative digests: a routine commit merged after a gated one would carry the gated change into production unapproved.
- **One environment with reviewers that routine runs bypass.** GitHub has no conditional reviewers; a custom protection rule needs its own GitHub App.
- **Previous source from `infra/releases/` on `main`, or from Dokploy's `GIT_SHA`.** The first lags behind until the recording PR merges; the second needs production secrets in the job that decides whether secrets are released.
- **Automatic rollback when the smoke fails.** Rejected as on staging: a running migration is never cancelled, and rolling back is a decision.

## Consequences and what is not verified

- Merging this changes nothing until the owner creates the production service and the `production` environment and sets the switch. The first deploy, and any deploy after 90 days without one, waits for the owner.
- **The record of a deploy is itself a gated change.** `infra/releases/**` is a gated path, so a PR that records a staging or production manifest is `risk:gated`, and the next promotion, which contains it, waits for the owner. Deploying that record produces a new manifest to record. While every deploy is recorded by its own PR, promotions therefore stay gated and routine ones are rare. This follows from the policy as written; whether manifests should be recorded differently (in batches, or as a routine path) is the owner's decision and a policy change.
- Labels are mutable after the merge. The `classify` workflow re-applies them on label events; agents never relabel a merged pull request. This is held by the rule, not by a setting.
- "Staging is green" means what `Deploy staging` checks today: both health endpoints with the SHA, the web root and an unknown route. The Playwright core-journey smoke does not run on staging yet.
- Not verified against GitHub, because no run exists: whether a job that waits for approval already holds the concurrency group (then later runs queue behind it and GitHub keeps only the newest queued one) or joins it only after approval (then several runs can wait at once); the design is safe under both, see the runbook. Whether `production-gated`'s "prevent self-review" stops the owner from approving a run that descends from the owner's own merge or dispatch. Whether the fourth workflow in the chain CI → publish → staging → production still starts (GitHub documents a limit of three chained `workflow_run` levels), in particular behind the catch-up workflow's dispatch.
- As on staging, `compose.deploy` takes `compose.dokploy.yaml` from the head of the configured branch, not from the exact source SHA.
